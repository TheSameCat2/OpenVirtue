# OV-20261029-inkey: how INKEY edits a string
Date: 2026-10-29
Status: confirmed (two rounds, scripted keys) and implemented
Observer: OpenVirtue maintainers (black-box probe, trace values)
Implementer: OpenVirtue maintainers

## Question
How does `INKEY` edit a string? The manual (p.85) says it:
- waits for [Return] like `WAIT`;
- aborts on [Esc], [Up], [Down], [PgUp] and [PgDn] with `RESULT` −1, 72, 80, 73 and 81, restoring
  the old content;
- edits with [BackSpace], [Del] and the cursor keys;
- stops at the string's declared length;
- cuts trailing spaces and sets `STR_LEN`.

It does not say:
- whether the input starts empty or from the old content;
- where the cursor starts, or what happens at the end;
- whether the world goes on while it waits.

## Why It Matters
The retail games enter save names with `INKEY`. OpenVirtue showed a blocking prompt that froze the
world, started from the old content's end, and deleted from the end.

## Setup
- Carriers: `ovtool oracle prepare inkey` (`tools/OpenVirtue.Tools/InkeyProbeCases.cs`), run with
  `ovtool oracle run`.
- Each case: the probe action arms a counting global slot, waits two cycles and calls `INKEY` on
  a string. Then it prints:
  - `TICKS`, the cycles counted and the count before;
  - `RESULT` and `STR_LEN`;
  - the string between brackets.
- Keys: `AUTOTYPE -w 10 -p 0.4 …` types them 10 s after launch. Round 1's `bksp` and `pgdn` are
  not DOSBox-X mapper names (the runs timed out); round 2 uses `bspace` and `pagedown`. `del` is
  not a mapper name either, so [Del] is not measured.

## Observations
| Old content | Keys | String after, `RESULT`, `STR_LEN` |
|---|---|---|
| `xxxxxxxx` | a b c Return | `abcxxxxx`, 0, 8 |
| `xxxxxxxx` | a b Esc | `xxxxxxxx`, −1, 8 |
| `xxxxxxxx` | a Up / a PgDn | `xxxxxxxx`, 72 / 81, 8 |
| `xxxxxxxx` | a b Space Space Return | `ab  xxxx`, 0, 8 |
| `xxxxxxxx` | Return | `xxxxxxxx`, 0, 8 |
| `xxx` | a b c d e Return | `abe`, 0, 3 |
| `hello` | BackSpace BackSpace p Return | `phell`, 0, 5 |
| `hello` | Right Right z Return | `hezll`, 0, 5 |
| `hello` | a b BackSpace c Return | `achel`, 0, 5 |

In every case the global slot went on counting while `INKEY` waited (250–400 cycles in the 10 s of
typing).

## Invariant
- **Old content and cursor.** The input edits the string's old content, with the cursor on its
  first character.
- **Typing.** A typed character is inserted at the cursor and the text is cut to the string's
  declared length. The cursor moves on but never past the last character, so typing at the end
  replaces it.
- **Editing keys.** [BackSpace] removes the character before the cursor, and does nothing on the
  first. [Right] and [Left] move the cursor over the text.
- **Ending.** [Return] ends the input with `RESULT` 0. [Esc], [Up], [PgUp], [Down] and [PgDn]
  restore the old content with their codes. `STR_LEN` is the resulting length.
- **The world.** It goes on while the input waits: global slots run.

## Open Questions
- [Del] and [Left] (unmeasured here: OpenVirtue removes the character at the cursor and moves the
  cursor back).
- Whether key hooks and object actions run during the input (OpenVirtue gives the game no keys).
- The cursor character 127 in a `TEXT` showing the string.

## Implementation
- `OpenVirtue.Engine.Interpreter.InkeyEditor` holds the editing rules.
- `RuntimeHost.EditInkey` feeds the window's keys to it frame by frame while the world runs, and
  completes the input. `IPlatformWindow.BeginTextInput`/`ConsumeTextKeys` carry the keys; the SDL
  window implements them, and other windows fall back to the blocking `Prompt`.
- Tests: `InkeyEditorTests` replay every measured sequence; `RuntimeHostInkeyTests` checks the
  world runs during the input.

## Addendum (2026-11-03): the carriers replayed, and the cycle the input ends in
The oracle-diff harness now replays the inkey carriers (`ovtool oracle diff`). DOSBox-X typed the
keys on its wall clock, so the trace has only two clock samples, `B` (before the `INKEY`) and `R`
(after it), each with `TICKS` and the cycles the global `EACH_TICK` slot counted. The replay takes
those two as its cadence samples and holds the keys until the frame before the original's `R`
cycle, so the input completes in that cycle.

With the action resumed at once when [Return] arrived, as OpenVirtue did, `R` landed in the right
cycle but a frame early on the clock (83.188 for 83.438, 0.25 tick, in every carrier): the count
printed after the `INKEY` was one ahead of the count printed before it over the same span of
frames. The original's `B` and `R` lines count alike: both are printed before the cycle's global
`EACH_TICK` slots, so the action coming out of `INKEY` resumes where one coming out of a `WAIT` does
(manual p.85: `INKEY` "waits for [Return] like `WAIT`"), in the cycle after the key, before the
global slots.

- **Invariant.** A completed `INKEY` resumes its action in the next cycle's resume slot, with the
  other waiting actions, not in the cycle the key was read.
- Implementation: `WdlRuntime.CompleteInput` queues the action as a `WAIT 0`; the host's
  `EditInkey` is unchanged. `Runtime_InkeyInstruction_*` tick once before the resumed statement.
- Result: 10 of the 13 carriers replay line for line (the three others, round 1's `backspace` and
  `pgdn` and round 2's `delete`, have empty original traces: their DOSBox-X key names were wrong).
- Harness: `OracleTrace.AutotypeTiming` (two lines whose ticks and counts rise together),
  `OracleReplay.InputEndDelay`, `HeadlessWindow.KeyDelayPolls`.
